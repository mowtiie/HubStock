# CLAUDE.md

## Project

HubStock: a multi-branch warehouse logistics app where branch managers request stock, a hub manager approves it, deliveries are scheduled, and the receiving branch accepts the delivery to update inventory.

Core flow: **Request Stock → Approve → Schedule Delivery → Replenish (Accept Delivery)**

This is a **simulation**. There is no backend, no payment gateway, no email/SMS, no real push notifications, no real tracking. Everything must look and behave correctly on screen during a demo. The only real storage is local SQLite: user accounts plus the app data (warehouses, products, stock, orders).

Source of requirements: the spec the user provides (Multiple Branches brief). Read it fully before building. Where the spec is vague, pick the simplest simulated behavior and note it here.

Status: all five build steps coded; step 6 polish in progress. Last verified build: assembleDebug passes. Emulator-checked so far: login, Hub home, approve with validation, delivery list, schedule screen. Not yet checked on a device: date pickers, dispatch, accept delivery, reports, inventory, warehouses, Branch and Clerk roles, dark mode.

## Prime directive: build the fastest way possible

- Speed beats elegance. Pick the shortest path that works in a live demo.
- **No structures.** No architecture patterns (MVVM, MVP, repositories, use cases, DI), no layers, no feature packages, no interfaces or abstract classes, no custom model/POJO classes. Exception: a single shared `GenericAdapter<T>` with a nested `Binder` interface.
- One Activity per screen, one shared `Data.java` holding public static fields and arrays for all app state.
- Represent records with parallel arrays and `ArrayList<String>` for lists that grow.
- Hardcode seed data. Never fetch or sync anything. `Data` lists are the in-memory working copy of the SQLite tables `warehouses`, `products`, `stock` and `orders`: `Data.load(context)` reads them, and every screen that changes them must call `Data.save(context)` afterwards. Data persists across restarts.
- Duplicate code freely if it is faster than abstracting it.
- No tests, no logging frameworks, no error handling beyond field validation.
- Do not add libraries or touch `build.gradle` dependencies. Enabling `buildFeatures { viewBinding = true }` is allowed.

## Build order

Build in this order. The core flow must work end to end before anything is polished.

1. Login, role home screens, and `Data.java` seed (warehouses, products, stock)
2. Inventory (products and per-warehouse stock) and warehouse information
3. Transfer request (Branch Manager) and approve/reject (Hub Manager)
4. Delivery scheduling and status advance (Hub Manager, Inventory Clerk), then replenish/accept delivery (Branch Manager)
5. Reports (Pending, Completed, Partial)
6. UI polish, then run the whole flow on an emulator and fix what turns up.

## Stack

- Java, XML layouts, AppCompat and Material 3, single `app` module. minSdk 24, targetSdk 36.
- No Fragments, no Navigation component, no Jetpack Compose. No permissions, no internet.
- Views via view binding. Use the generated `*Binding` classes, never `findViewById`.
- Lists: `RecyclerView` with the one shared `GenericAdapter<T>` and shared row layout `item_row.xml`. Never write a per-screen adapter.
- Database: pure SQLite (`SQLiteOpenHelper`, `ContentValues`, `Cursor`). No Room, no ORM, no DAO layer.
- Dropdowns: `TextInputLayout` (ExposedDropdownMenu style) with `MaterialAutoCompleteTextView`. Never `Spinner`.
- Messages: `Snackbar` for validation and errors on a screen that stays open. `Toast` only for simulated notifications and messages shown as a screen closes. `MaterialAlertDialogBuilder` (never plain `AlertDialog.Builder`) for dialogs, `BottomSheetDialog` for add/edit sheets.

## Code layout

Package `com.mowtiie.hubstock`, three flat folders. Do not nest them or add per-feature packages.

- `activities/`: every Activity.
- `data/`: `Data.java` (all state and helpers) and `DbHelper.java`.
- `adapters/`: `GenericAdapter.java`.

Navigation is `startActivity(new Intent(...))` with `putExtra`. After a flow finishes, start the final screen with `NEW_TASK | CLEAR_TASK`. Logout clears the task and returns to Login.

## UI rules

- Material 3 components, not plain framework widgets: `MaterialToolbar`, `MaterialTextView`, `MaterialButton`, `MaterialCardView`, `MaterialDivider`, `TextInputLayout` with `TextInputEditText`, `MaterialSwitch`, `TabLayout`, `Chip`/`ChipGroup`, progress indicators.
- Every screen except Login has a `MaterialToolbar` with a title and a back arrow (content description set), except root screens.
- Toolbar actions use menu resources via `app:menu` and `setOnMenuItemClickListener` (no `setSupportActionBar`).
- Empty lists use a shared `view_empty.xml` through `<include>`.
- Quantities show with their unit (for example `12 pcs`) through one helper, `Data.qty(int, String)`. No money anywhere in this app.
- Theme: generated by Material Theme Builder (`themes.xml`, `colors.xml`, `theme_overlays.xml`). Do not hand-edit. Colors come only from `?attr/color*` and `?attr/textAppearance*`. No hex values or custom colors.
- Page background and toolbars `colorSurfaceContainer`, sticky bars `colorSurfaceContainerHigh`, brand accents `colorPrimary`, secondary actions tonal, one filled button per screen.
- Insets: `EdgeToEdge.enable(this)` right after `super.onCreate` in every Activity, `fitsSystemWindows="true"` on every layout root. Auth screens sit in a `ScrollView` with `fillViewport="true"`.
- Spacing: screen padding 16dp (24dp on auth), gaps 8dp between fields and cards, 16dp between sections. Lists use `clipToPadding="false"` with 8dp bottom padding.
- Dividers only above a sticky bottom bar or between distinct sections, never under a toolbar or between a heading and a list.
- Chips are for interactive items (status filters). Static facts, including an order's status, go in text.
- Destructive actions offer a Snackbar Undo.
- Accessibility: content descriptions on icons, 48dp touch targets, decorative emoji hidden from screen readers.

## Forms

- Every `TextInputLayout` has helper text with the format when it matters.
- Validate with inline `setError` on the wrong field, not a generic Snackbar. Clear the error on the next attempt.
- Password fields use the toggle end icon, 6+ characters. Emails use `Patterns.EMAIL_ADDRESS`.
- Dates are picked with `MaterialDatePicker` / `MaterialTimePicker` into a read-only field.

## Naming and style

- Constants `ALL_CAPS_WITH_UNDERSCORES` (roles, statuses, extra keys).
- View ID prefixes: `til`, `et`, `dd`, `tv`, `btn`, `rv`, `chip`, `sw`, `card`, `ll`.
- 4-space indent, `binding.xxx` access, lambdas for click listeners. Match surrounding code.
- Comments only when the reason is not obvious.

## Account defaults

- Login and logout are fake but validated. There is no sign up, password reset or profile edit. Accounts live in the SQLite `users` table (with `role` and `warehouse` columns), and the logged-in user is copied into `Data.USER_*` including `USER_ROLE` and `USER_WAREHOUSE`.
- Three roles: Hub Manager, Inventory Clerk, Branch Manager. Login has no role switch: the stored account decides which home screen opens. Each role has its own root screen (`HubManagerHomeActivity`, `ClerkHomeActivity`, `BranchHomeActivity`), and Logout is only on Profile.
- Accounts are created automatically on first launch, all with password `demo1234`: `hub@demo.com` (Hub Manager), `clerk@demo.com` (Inventory Clerk), `branch.a@demo.com` (Branch Manager of Branch A), `branch.b@demo.com` (Branch Manager of Branch B).
- Seed demo data on first login of any role (warehouses, products, stock, a few transfer orders in different statuses) so no screen is empty in a demo. Keep it in one `Data.seedDemo(context)` helper: it loads saved data once per process and seeds and saves only if the tables are empty.
- Never put a role's screens behind a check in the UI only. Every role-specific Activity is reached from that role's home screen.
- Light and dark mode are both supported through the generated theme. Do not hardcode colors.
- Never use real Android notifications or channels. Simulated messages are Toast or Snackbar only.

## App-specific rules

**1. Roles and permissions**

| Action | Branch Manager | Inventory Clerk | Hub Manager |
|---|---|---|---|
| Create transfer request | own warehouse | no | no |
| Approve / reject request | no | no | yes |
| Manage products and stock | view own | yes | yes |
| Schedule delivery, advance status | no | yes | yes |
| Accept delivery (replenish) | own warehouse | no | no |
| View reports | own branch | all | all |
| Manage warehouses | no | no | yes |

**2. Product records / inventory**
- Product catalog is global: SKU, name, unit, category. Stock is per warehouse: parallel arrays `STOCK_WAREHOUSE`, `STOCK_PRODUCT`, `STOCK_QTY`.
- Hub Manager and Clerk can add/edit products and adjust stock with a `BottomSheetDialog`. Branch Manager sees only their own warehouse's stock.
- Low stock (qty below a hardcoded `LOW_STOCK_LEVEL`) shows a text warning in the row.

**3. Warehouse information**
- Warehouse has name, location, and branch manager (picked from the seeded Branch Manager accounts, shown by name). Hub Manager adds/edits via bottom sheet.
- The Hub is itself a warehouse named "Central Hub" and holds stock. It is the default source for requests.

**4. Product transfer order**
- The requester is the destination. A Branch Manager picks the source warehouse (default Central Hub), one product, and a quantity.
- One product per order, to keep the data in flat parallel arrays. No multi-line orders.
- Validation: quantity is greater than 0 and not above the source's available stock, shown with `setError`.
- Hub Manager approves with an approved quantity (defaults to requested, can be lowered but not above source stock) or rejects with a reason.
- Statuses are constants: `PENDING`, `APPROVED`, `REJECTED`, `SCHEDULED`, `IN_TRANSIT`, `COMPLETED`, `PARTIAL`.
- Lifecycle: `PENDING → APPROVED → SCHEDULED → IN_TRANSIT → COMPLETED or PARTIAL`, or `PENDING → REJECTED`.

**5. Delivery schedule (stock transfer delivery)**
- Hub Manager or Clerk sets dispatch date and expected arrival date with `MaterialDatePicker` for an `APPROVED` order, moving it to `SCHEDULED`.
- A "Dispatch" button moves it to `IN_TRANSIT` and deducts the approved quantity from the source's stock. A "Delivery list" screen shows scheduled and in-transit deliveries.
- Transit is simulated by the manual Dispatch button. No timers, no maps, no tracking.

**6. Replenish (delivery accepted by branch)**
- The Branch Manager opens an `IN_TRANSIT` order for their warehouse and enters the received quantity (defaults to the approved quantity, cannot exceed it).
- Received equals approved: status `COMPLETED`. Received is less than approved: status `PARTIAL`, and the shortfall is shown on the order.
- Accepting adds the received quantity to the destination's stock.
- Stock changes only on dispatch (source) and on accept (destination). Approval does not reserve stock.

**7. Reports**
- One screen with a `TabLayout`: Pending, Completed, Partial. Each tab lists matching orders from `Data` using the shared adapter, with a count at the top.
- Branch Manager sees only orders where their warehouse is the source or destination. Hub Manager and Clerk see all.
- Order completion and transfer completion are the same thing here. External supplier purchase orders are out of scope.

**8. Access control**
- Accounts are seeded in SQLite with the `role` column. Role-specific Activities are reached only from that role's home screen.
- Hub Manager home: pending approvals, warehouses, inventory, deliveries, reports, profile.
- Clerk home: inventory, deliveries, reports, profile.
- Branch Manager home: new request, my orders, incoming deliveries, my stock, reports, profile.

## Screens (one Activity each)

Auth and shared:
- `LoginActivity` (launcher)
- `ProfileActivity` (shows account details, logout)

Role homes (root screens):
- `HubManagerHomeActivity`
- `ClerkHomeActivity`
- `BranchHomeActivity`

Features:
- `InventoryActivity` (products and stock, add/edit via bottom sheet)
- `WarehouseListActivity` (Hub Manager, add/edit via bottom sheet)
- `TransferRequestActivity` (Branch Manager, new request)
- `TransferOrderListActivity` (filtered by `putExtra`: pending approvals, my orders, all)
- `TransferDetailActivity` (approve/reject, schedule, dispatch, accept, depending on role and status)
- `DeliveryListActivity` (scheduled and in-transit)
- `ScheduleDeliveryActivity` (dates)
- `ReceiveDeliveryActivity` (received quantity)
- `ReportsActivity` (Pending, Completed, Partial tabs)

## Manifest

- Only `LoginActivity` (launcher) is `exported="true"`. Every other Activity is `exported="false"`. Register every new Activity.

## Release

- `release` uses `isMinifyEnabled = true` and `isShrinkResources = true`. Add keep rules to `proguard-rules.pro` only when a release crash needs one.
- Signing reads `keystore.properties` in the project root (see `keystore.properties.example`). Never commit `keystore.properties`, `*.jks` or `*.keystore`.
- Verify with `apksigner verify --print-certs --verbose <apk>`.
